# 作業の委任(サブエージェント)

原則は「その作業に足りる一番安い手段を選ぶ」。委任1回の入場料はコンテキスト 23k〜34k トークン(2026-08-24、transcript の usage を実測)で、委任先は毎回ゼロからコンテキストを積む独立セッションになる。数分で終わる作業の委任は割に合わない。

| 手段 | 使う場面 |
|---|---|
| 自分でやる | 2〜3ファイル読めば済む確認、1文で説明できる差分、往復の多い対話的デバッグ、ユーザーと詰めながら進める設計議論 |
| Explore / Plan サブエージェント | 単発の探索・調査で結果だけ欲しいとき。CLAUDE.md と git status をスキップするので軽い |

- 複数のエージェントに投げたときは、各エージェントの結果を自分で検証してから集約する。「エージェントがそう言った」を根拠にしない

# 作業スタイル全般

- **「調査 → 理解 → ユーザーの確認」を、実装前の独立したステップとして踏む。** 原因や仕組みを把握しても、いきなり修正に入らない。理解した内容を提示してユーザーの納得を得てから実装に着手する
- 「事実」と「仮説」を明確に区別して書く。自分で確認したこと(コードを読んだ・実行した・ドキュメントに明記されている)と、伝聞・未検証の推測を混ぜない。節を分けるか、検証済みか否かを注記する
- ユーザーが明示的に保留した作業は、「その作業をやって」という指示があるまで着手しない。「続けて」は直前にやっていた(中断された)作業の継続のみを指す。迷ったら着手せずに確認する
- Git・インフラの専門用語(worktree、fetch、リモートとローカルの関係など)を使うときは、図やアナロジーを交えて噛み砕いて説明する
- ルールや前提事実を訂正・追加したときは、その変更が影響する他のセクション・関連ドキュメントも自分から洗い出して一緒に修正する。指摘された1箇所だけ直して終わりにしない(2026-08-24、DBの確認方法ルールを追加した直後、関連ドキュメントの更新漏れを指摘された)

# 文章作成のルール

- **比較には表やマトリクス図を使う。** 選択肢や項目を2つ以上比較するときは、箇条書きを並べるのではなく表(Markdownテーブル)で軸を揃えて提示する。観点(コスト・リスク・適用条件など)を列、比較対象を行(またはその逆)に置くと、どの観点で差がついているかが一目で分かる
- **説明・分析は論理的な文章(prose)で書き、箇条書きの羅列に頼らない。** 基本形は「主張(結論) → 根拠 → 具体例・引用」(PREP法)。仮説を提示するときは根拠を並べるだけで終わらせず、その根拠がなぜその結論を支えるのか(Toulminモデルの claim-grounds-warrant に相当する、根拠と結論をつなぐ推論の部分)まで書く。箇条書きは、手順・チェックリスト・ファイルパスの列挙など、順序や列挙そのものが情報である場面に限定する
- **開発関連の調査は一次情報(ソースコード・DBの実データ)を参照する。** 下記「調査の進め方」の一次情報ルールと同じ原則で、伝聞やドキュメントの記載だけで済まさない。DBの実データを直接確認できない場合は、推測で断定せずユーザーに調査を依頼する(環境ごとの確認手段は下記「調査の進め方」のDB確認ルールに従う)
- **調査を依頼する文章も論理的に書く。** 見てほしいテーブル名・条件・カラムを挙げるだけでなく、なぜその確認が必要なのか(検証したい仮説)、その結果が次の判断にどう使われるのかを含めて依頼する

# コードを書くときのルール

- **コメントは「なぜそうなっているか」だけを書く。「何をしているか」は書かない**(2026-10-15ルール化)。処理の内容はコードを読めば分かるので、逐語訳のコメントは行数を増やすだけで情報を増やさない。書く価値があるのは、コードを読んでも分からないことに限る — 他ファイルや他システムとの対応関係、業務上の制約、あえて非自明な書き方をしている理由、既知の落とし穴
  - 書かない: 変数代入やメソッド呼び出しの言い換え、引数の説明(シグネチャで分かる)、メソッド名やテスト名で既に説明していることの繰り返し
  - 書く: `# V1::ShopPortal::SessionsController rejects these unless the source IP is allowed.` のように、その値がどこの何と対応しているかを示すもの
  - **迷ったら消す。** コメントはコードと一緒に腐るので、間違ったコメントが残るくらいなら無いほうが安全
- **これはドキュメント(backlog doc)の書き方とは意図的に逆の方針である。** docでは読み手を初心者と想定して「コードを引用したらその行が何をしているかを日本語で説明する」(aftee側 CLAUDE.md の「ドキュメントの書き方」)。docは理解のための読み物、コード内コメントは保守のための注記であり、目的が違うため使い分ける

# 調査の進め方

- **調査結果は必ずコードを一次情報とし、パスとコード片を引用して根拠を示す。** 伝聞やドキュメントの記載だけで済まさない
- **ドキュメントに残す参照は、そのPCが無くても辿れる形で書く(2026-09-01ルール化)。** チャット上の説明では `path/to/file.rb:123` 形式でよいが、md ファイルに残すときは下記に従う。ローカルの絶対パスに依存した参照は、別のマシンで読んだ瞬間に価値がゼロになるため
  - **コードの参照は GitHub のリンクにする。** ラベルは `<リポジトリ名>/<パス>:<行>` にして、リンク先を `https://github.com/<org>/<リポジトリ名>/blob/<ブランチ>/<パス>#L<行>` にする。ラベルにパスと行番号を残すので、リンクが使えない環境でも情報は落ちない
  - **ローカルの絶対パス(`~/...` や `/Users/...`)をコード引用に使わない。** ただしワークスペースの構成説明やシェル手順(`cd ~/work/<repo>` など)はそのままでよい
  - **リポジトリ名を省略したパス(`app/models/user.rb` など)も書かない。** どのリポジトリか分からず辿れない
  - **他のドキュメントへの参照はリンクにせず平文で書く**(例: `doc-96「タイトル」を参照`)。相対パスのリンクはファイル移動で壊れ、wikilinkは特定のビューア以外では機能しない
  - 業務ワークスペース固有の適用ルール(ブランチの選び方・GitHubに無いリポジトリの例外・リンクの検証コマンド)は、業務側のドキュメント管理リポジトリに置く
- 処理の流れやファイル間の関係は mermaid 図(sequence diagram / flowchart)で示すのを標準にする。作図ルールは `mermaid-rules` skill にあるので、図を書く前に読む
- **DBの実データを確認する必要があるときは、環境によって手段が違う。** 接続手順が整備されている環境(手順はプロジェクト側の CLAUDE.md にある)では、Claude が psql で直接確認してよい。整備されていない環境・および本番環境は、Claude が接続せず Postico で目視確認してもらう。後者の場合、接続は既に確立されている前提でよく、見てほしいテーブル名・条件・カラムを具体的に伝える(2026-09-01ルール変更。旧ルールでは環境を問わず常に Postico 目視確認としていた)
- **共有環境のDBに対して実行してよいのは読み取りだけ。** `INSERT` / `UPDATE` / `DELETE` / `TRUNCATE` / `ALTER` / `DROP` とそれらを含むトランザクションは、ST・CT・本番など**他人と共有する環境では一切実行しない**。「確認のために書いて戻す」も禁止。書き込みが必要になったら、自分で実行せず SQL をユーザーに提示して判断を仰ぐ
  - **例外は、自分で作って壊してよいローカルのDBだけ**(2026-10-13追記)。テスト用DBにデータを入れてマイグレーションの制約を検証する、といった用途は対象外。目的は共有環境の実データを守ることであって、書き込みという操作自体の禁止ではない
- **SQL は `EXPLAIN` でコストを見積もってから実行する。** いきなり本実行しない。手順は ①`EXPLAIN`(付けるだけではクエリは実行されない)で `cost` と推定行数を確認する → ②見積もりが大きければ絞り込み条件・対象期間・`LIMIT` を足して下げる → ③許容範囲に収まった SQL を本実行する、の3段階。実行計画の読み方は業務側のドキュメント管理リポジトリを参照
- **実データの取得は必要最小限に絞る。** `SELECT *` は使わず列を明示列挙し、まず `count(*)` や `group by` の集計で答えが出ないかを先に考える。生レコードが必要なときは `LIMIT` を付ける。理由は、クエリ結果がそのまま会話ログに残るため。個人情報を含むテーブルでは特に重要

# skill / ツールの使い分け

- 設計や計画を深掘りするときは `/grill-me` を使う。`disable-model-invocation: true` の skill は Claude 側から起動できないので、設計がまとまってきたタイミングでユーザーに提案する形にする
- skill を作るときは skill-creator を使う。official marketplace(claude-plugins-official)の plugin なので、available skills に見当たらなければ `/plugin` からのインストールを案内する
- `rm` は組織のポリシー設定(`~/.claude/remote-settings.json` の `permissions.deny`)で禁止されている。ファイル削除が必要なときは自分で試さず、コマンドを提示してユーザーに実行してもらう
