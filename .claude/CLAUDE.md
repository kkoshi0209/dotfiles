# Herdr

タスクを依頼されたら、ユーザーが明示的に言及していなくても、常にherdrスキルを使って作業すること。

タスクが独立した複数のサブタスクに分割できる場合(例: 複数リポジトリにまたがる別々の調査、並行して進められる複数の作業)、自分一人で全部抱え込まず、herdrで各サブタスクごとにペイン(必要ならタブ)を分けてエージェントを立ち上げ、並行して進めること。自分は司令塔として各エージェントに指示を出し、結果を集約・検証してユーザーに報告する役割に回る。

**単発の調査・実装作業でも同様。** ちょっとした読み取り専用の確認を除き、まとまった作業(コード調査、実装計画の検討、実装そのものなど)を行うときは、原生のAgent/Explore/Planツール(このセッション内で動く一時的なサブエージェント)ではなく、herdrでペインを分けて専用のエージェントを起動し、そちらに作業させること。単一のタスクだから並列化の必要が無い、という理由でherdrを使わない判断はしない。plan modeのExplore/Planフェーズも例外ではない。

**再帰的な委任を防ぐため、herdrでサブエージェントに作業を投げるときは、必ずプロンプト中に「これは既にherdr経由で委任された作業であり、受け手はさらにherdrで別エージェントを立てて委任するのではなく、自分自身のRead/Grep/Edit等のツールで直接作業を完了させること」という趣旨の一文を含める。** これを怠ると、委任されたエージェントも同じ「常にherdrを使う」というこのグローバル指示に文字通り従ってしまい、自分もさらにherdrで委任し、それがまた繰り返される……という形でネストが際限なく深くなる(2026-08-20、売上確定ロジック調査で4段階以上のネストが発生し、互いを監視し合うだけで進捗が止まる事故が実際に起きた)。単発の委任で完結させるのが基本で、真に並列化すべき独立したサブタスクがある場合だけ、受け手からもう一段ペインを分けてよいと明示的に許可した時に限る。

**不要になったペイン・タブは、都度(ユーザーに指摘される前に)片付けること。** そのエージェントの成果(調査結果・作成物)をbacklog docやユーザーへの報告に確実に回収し終えたら、その時点でペイン(必要なら空になったタブも)を閉じる。「後でまとめて掃除する」のではなく、1つのサブタスクが完了して結果を回収し終えるたびに閉じるのが基本。

# 作業スタイル全般

- **「調査 → 理解 → ユーザーの確認」を、実装前の独立したステップとして踏む。** 対象を調査して原因や仕組みを把握したら、いきなり修正に入らない。理解した内容を提示してユーザーの納得を得てから実装に着手する
- **「事実」と「仮説」を明確に区別して書く。** 自分で確認したこと(コードを読んだ・実行した・ドキュメントに明記されている)と、伝聞・未検証の推測を混ぜない。ドキュメントやチャットでの説明で、節を分ける・検証済みか否かの注記を添えるなどして区別する
- **ユーザーが明示的に保留した作業は、「その作業をやって」という明確な指示があるまで着手しない。** 「続けて」は直前にやっていた(中断された)作業の継続のみを指すと解釈する。迷ったら着手せずに確認する
- **Git・インフラの専門用語(worktree、fetch、リモートとローカルの関係など)を使うときは、図やアナロジーを交えて噛み砕いて説明する。** 前提知識を仮定しすぎない
- **ルールや前提事実を訂正・追加したときは、その変更が影響する他のセクション・関連ドキュメントも自分から洗い出して一緒に修正する。** 指摘された1箇所だけ直して終わりにせず、同じ前提の上に成り立っている記述が他にないか確認する(2026-08-24、DBの確認方法ルールを追加した直後、関連ドキュメントの接続手順セクションの更新漏れを指摘された)

# 調査の進め方

- **調査結果は必ずコードを一次情報とし、該当ファイルパスとコード片を引用して根拠を示す。** 伝聞やドキュメントの記載だけで済まさず、実装を確認できる場合は実際に読んだコードの場所(`path/to/file.rb:123` のような形式)と該当箇所の中身を引用して裏付ける
- **処理の流れやファイル間の関係は、必ずmermaid図(sequence diagram/flowchart)で示す。** 文章だけの説明で済ませず図示することを標準にする(作図ルールは下記「図の書き方」参照)
- **DBの実データを確認する必要があるときは、Claude自身がSQLクライアントで接続して確認するのではなく、Posticoで目視確認する。** 接続は既に確立されている前提で進めてよい。確認してほしい内容(テーブル名・条件・見るべきカラム)を具体的に伝え、実際の値の確認はユーザーにPosticoで行ってもらう

# 図の書き方(mermaid)

過去に何度も文字被り・構文エラーを起こしているため、mermaid図を書いたら以下を必ず見直す。

1. 矢印は subgraph(箱)そのものではなく、**箱の中の具体的なノード**に向ける(`A --> subgraphID` ではなく `A --> nodeInsideSubgraph`)
2. 複数の subgraph を横に並べて矢印を交差させる図は `flowchart TB` ではなく **`flowchart LR`** にする
3. ドット線にラベルを付けるときは前後にスペースを入れる(`-. text .->`。`-.text.-` は構文が壊れることがある)
4. **同じ2つのノードを逆向きの矢印2本(A→B と B→A)で結ばない。** mermaidが重ねて描画しラベルが重なる。「行き」の1本だけ描き、「戻り」は図の下に文章で書く
5. **subgraph のタイトルに `<br>` で改行を入れない**(1行の短いタイトルにする)。特に中に円柱型(DB)ノードがあると、タイトルが2行になった瞬間に中のノードとぶつかる。長い説明はノード側のラベルに書く
6. **ノードのテキストが長い/ノード数が4つ以上ある一直線のチェーン図(subgraphを横に並べる図ではない場合)は `flowchart LR` ではなく `flowchart TB` にする。** LRで長文ノードを横に並べると図全体が横に伸びすぎて文字が読めなくなる。LRを使うのはルール2の「subgraphを横に並べて矢印が交差する」ケースに限定する
7. **ノード内で `<br>` / `<br/>` による改行を使わない。** 多くのレンダラー(HTMLタグを解釈しないMarkdownビューア等)では`<br>`がそのまま文字列として表示されてしまう。**1ノードのテキストは1行の短い文言に収め、長い説明は複数のノードに分割してチェーンで繋ぐ**(例: `h1["仮説1: ○○"] --> v1["検証: △△"] --> r1["結果: ×××"]`)。補足の詳細は図の下に文章で書く

# skill / ツールの使い分け

- **設計や計画を深掘りするときは `/grill-me` を積極的に使う。** `disable-model-invocation: true` のスキルはClaude側からは起動できないため、設計がまとまってきたタイミングで「/grill-me で深掘りしましょう」と**ユーザーに提案する**形にする
- **skillを作るときは skill-creator を使う。** official marketplace(claude-plugins-official)のpluginなので、available skills に見当たらなければ `/plugin` からのインストールを案内する
