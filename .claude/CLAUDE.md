# 作業の委任(サブエージェント)

原則は「その作業に足りる一番安い手段を選ぶ」。委任1回の入場料はコンテキスト 23k〜34k トークンで、委任先は毎回ゼロからコンテキストを積む独立セッションになる。数分で終わる作業の委任は割に合わない。

| 手段 | 使う場面 |
|---|---|
| 自分でやる | 2〜3ファイル読めば済む確認、1文で説明できる差分、往復の多い対話的デバッグ、ユーザーと詰めながら進める設計議論 |
| `researcher` | 複数ファイルを読む調査で、結果だけ欲しいとき |
| `doc-writer` | mermaid 図を含む Markdown 成果物を書かせるとき。作図・文体・自己レビューの skill をプリロード済み |
| `Explore` / `Plan` | 単発の探索・計画。CLAUDE.md と git status をスキップするので軽い |

複数のエージェントに投げたときは、各エージェントの結果を自分で検証してから集約する。「エージェントがそう言った」を根拠にしない。

# Skillを作るとき

新しい skill を作成・更新するときは、素手で `SKILL.md` を書かず `skill-creator` skill を使う。構成・frontmatter・ディレクトリ配置のベストプラクティスを踏まえたひな形を作ってくれるため。

# 作業スタイル全般

- **「調査 → 理解 → ユーザーの確認」を、実装前の独立したステップとして踏む。** 原因や仕組みを把握しても、いきなり修正に入らない。理解した内容を提示してユーザーの納得を得てから実装に着手する
- 「事実」と「仮説」を明確に区別して書く。自分で確認したこと(コードを読んだ・実行した・ドキュメントに明記されている)と、伝聞・未検証の推測を混ぜない。節を分けるか、検証済みか否かを注記する
- **今どの抽象レベルの話をしているかを意識し、具体 → 抽象 → 具体を行き来しながら問題を解く。** 具体的な事象だけを追うと全体像や再発防止策を見失い、抽象的な議論だけに留まると目の前の事実とずれていく。調査・デバッグ・設計のどの場面でも、個別の事実から共通するパターンや原因(抽象)を見出し、それを再び具体的な検証・対策に落とし込むサイクルを意識して回す。文章にこの往復を明示するかどうかは別の話で、書き方は `writing-rules` skill にある
- ユーザーが明示的に保留した作業は、「その作業をやって」という指示があるまで着手しない。「続けて」は直前にやっていた(中断された)作業の継続のみを指す。迷ったら着手せずに確認する
- Git・インフラの専門用語(worktree、fetch、リモートとローカルの関係など)を使うときは、図やアナロジーを交えて噛み砕いて説明する
- **ルールや前提事実を訂正・追加したときは、その変更が影響する他のセクション・関連ドキュメントも自分から洗い出して一緒に修正する。** 指摘された1箇所だけ直して終わりにしない
- **成果物を出す前に `self-review` skill の手順で自己レビューする。** 対象は調査報告・設計案・ドキュメント・PR説明文・コミットメッセージ・コード変更・複数段落の説明。1行の回答やコマンド実行結果の報告は対象外

# 文章作成のルール

**文章の品質基準はグライスの会話の公理(協調の原理)に置く。** チャットの回答・調査報告・ドキュメント・PR説明文のすべてが対象。以下の項目も、他の節の文章まわりのルールも、いずれも4公理の適用例にあたる。**個別のルールが無い場面では、ここに立ち返って判断する。**

- **量(Quantity)** — 求められているだけの情報を与え、それ以上は与えない。ただし「求められている量」は読み手で決まるので、初心者向けの用語解説は冗長ではなく、むしろこの公理を満たすために必要
- **質(Quality)** — 偽だと思うこと、十分な証拠のないことを言わない
- **関係(Relation)** — 関連のあることを言う。聞かれていない余談、不要な自己訂正を足さない
- **様態(Manner)** — 明晰であれ。不明瞭・曖昧を避け、簡潔に、順序立てて

そのうえで:

- **比較には表を使う。** 選択肢や項目を2つ以上比較するときは、箇条書きを並べるのではなく Markdown テーブルで軸を揃える。観点(コスト・リスク・適用条件など)を列、比較対象を行に置くと、どの観点で差がついているかが一目で分かる
- **説明・分析は論理的な文章(prose)で書き、箇条書きの羅列に頼らない。** 基本形は「主張(結論) → 根拠 → 具体例」。仮説を提示するときは根拠を並べるだけで終わらせず、その根拠がなぜその結論を支えるのか(Toulmin モデルの warrant)まで書く。箇条書きは、手順・チェックリスト・列挙そのものが情報である場面に限る
- **調査を依頼する文章も論理的に書く。** 見てほしいテーブル名・条件・カラムを挙げるだけでなく、なぜその確認が必要なのか(検証したい仮説)、結果が次の判断にどう使われるのかを含める
- **文章を書く前に `writing-rules` skill を読む。** AIが書いたと分かる言い回し、抽象と具体の往復、蛇足の削り方はそこにある。この節が「何を基準に判断するか」、skill が「どう書くか」という分担

# コードを書くときのルール

**コードは人間が読む前提で書く。** 動くことは最低条件であり、他の人(未来の自分を含む)が読んで理解できることを基準にする。可読性を測る物差しは「コメント無しで意図が伝わるか」であり、以降のコメントのルールはこの基準を満たせなかったときの最後の手段として読む。

**そもそもコメントが要らないコードを書くことを目指す。** コメントを書きたくなったら、先に命名や関数分割で同じ意図を表現できないか検討する。「何をしているか」を補うコメントは、たいてい命名か構造の見直しで消せる。

**コメントは「なぜそうなっているか」だけを書く。「何をしているか」は書かない。** 処理の内容はコードを読めば分かるので、逐語訳のコメントは行数を増やすだけで情報を増やさない。書く価値があるのは、コードを読んでも分からないことに限る — 他ファイルや他システムとの対応関係、業務上の制約、あえて非自明な書き方をしている理由、既知の落とし穴。

- 書かない: 変数代入やメソッド呼び出しの言い換え、引数の説明(シグネチャで分かる)、メソッド名やテスト名で既に説明していることの繰り返し
- 書く: `# V1::ShopPortal::SessionsController rejects these unless the source IP is allowed.` のように、その値がどこの何と対応しているかを示すもの
- **迷ったら消す。** コメントはコードと一緒に腐るので、間違ったコメントが残るくらいなら無いほうが安全

**これはドキュメントの書き方とは意図的に逆の方針である。** doc は理解のための読み物、コード内コメントは保守のための注記であり、目的が違う。

言語のイディオム(Rubyのイテレータ、短絡評価など)は可読性を上げるなら使うが、「その言語らしい書き方」自体を目的にしない。素直な書き方の方が読みやすいなら、イディオムより可読性を優先する。階層構造・抽象化・継承に関する具体的な原則は `software-architecture` skill に、Ruby固有の判断基準は `~/aftee/CLAUDE.md` の「コード設計の観点」に置く。

# 調査の進め方

- **調査結果は必ずコードを一次情報とし、パスとコード片を引用して根拠を示す。** 伝聞やドキュメントの記載だけで済まさない。DBの実データを直接確認できない場合も、推測で断定せずユーザーに調査を依頼する
- 処理の流れやファイル間の関係は mermaid 図で示すのを標準にする。作図ルールは `mermaid-rules` skill にあるので、図を書く前に読む
- **共有環境(ST・CT・本番)のDBに対して実行してよいのは読み取りだけ。** 書き込みが必要になったら、自分で実行せず SQL をユーザーに提示して判断を仰ぐ。例外は自分で作って壊してよいローカルDBだけ。接続手順・`EXPLAIN` での見積もり・取得を絞る理由は `aftee-db` skill にある

## ドキュメントに残す参照の書き方

チャット上の説明では `path/to/file.rb:123` 形式でよいが、md ファイルに残すときは下記に従う。ローカルの絶対パスに依存した参照は、別のマシンで読んだ瞬間に価値がゼロになるため。

- **コードの参照は GitHub のリンクにする。** ラベルは `<リポジトリ名>/<パス>:<行>`、リンク先は `https://github.com/<org>/<リポジトリ名>/blob/<ブランチ>/<パス>#L<行>`。ラベルにパスと行番号を残すので、リンクが使えない環境でも情報は落ちない
- **ローカルの絶対パス(`~/...` や `/Users/...`)をコード引用に使わない。** ワークスペースの構成説明やシェル手順(`cd ~/work/<repo>` など)はそのままでよい
- **リポジトリ名を省略したパス(`app/models/user.rb` など)も書かない。** どのリポジトリか分からず辿れない
- doc 間の参照の書き方はドキュメント管理リポジトリごとに決まる。backlog の場合は `aftee-docs` skill を参照

# ツールの制約

`rm` と `ssh` は組織のポリシー設定(`~/.claude/remote-settings.json` の `permissions.deny`)で禁止されている。必要なときは自分で試さず、コマンドを提示してユーザーに実行してもらう。
