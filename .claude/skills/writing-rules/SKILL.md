# 文章を書くときのルール

目指すのは、仕事のできる人が書いた文章に見えること。AIらしい癖は読みにくいだけでなく、人が書いた文書として扱ってもらえなくなる。

判断の基準そのものは `~/.claude/CLAUDE.md`「文章作成のルール」のグライス4公理にある。ここに書くのはその具体化で、「どう書くか」を扱う。箇条書きと散文の使い分け、比較に表を使う原則は CLAUDE.md 側にあるので再掲しない。

## 1. 抽象と具体を往復させる

主張(抽象)を置き、根拠を示し、具体例(具体)で着地させる。抽象だけの段落は何も伝えず、具体だけの段落は何のための話か分からない。

長い説明では、具体例を出したあとに一段抽象へ戻して「つまり何が言えるか」を書く。ここを省くと、読み手は事実の羅列から自分で結論を組み立てることになる。

これは書いた文章の見せ方の話。問題を解く過程そのもので具体と抽象を行き来する話は `~/.claude/CLAUDE.md`「作業スタイル全般」にある。

## 2. 結論を先に置く

結論(今いちばん伝えたいこと)を文章やチャット回答の冒頭に置き、経緯・調査過程・根拠はその後に続ける。背景説明から書き始めて結論を最後に置くと、読み手は最後まで要点をつかめないまま読み進めることになる。

節が複数ある文章では、各節の冒頭にもその節の結論を置く。節の本文を最後まで読まないと言いたいことが分からない構成は避ける。

これは項目1「抽象と具体を往復させる」の主張→根拠→具体という論証内部の順序を、文章全体・節単位のスケールに適用したもの。項目1が1つの主張をどう支えるかの話であるのに対し、これは複数の主張・情報のうちどれを先に出すかの話。

## 3. 読み手を特定してから書く

書き始める前に誰が読むかを決める。決めないまま書いた文章は、前提の説明が多すぎるか少なすぎるかのどちらかになる。

人に共有される前提で書く。自分の環境に依存した記述(ローカルの絶対パス、自分だけが知っている経緯、この会話でしか通じない「さっきの件」)を残さない。必要な文脈はその場に要約して埋め込む。

## 4. 蛇足を削る — 段落削除テスト

書き終えたら、任意の段落を1つ消して読み直す。意味が通ってしまうなら、その段落は要らないか、他の段落に溶かすべきだった。

機械的に生成された文章は構成が均質で、1段落抜いても滑らかに読めてしまう。裏を返せば、どの段落も抜けない状態に書けていれば、その文章は冗長ではない。

要約・本文・まとめで同じことを3回書かない。繰り返しそうになったら参照で済ませる。

## 5. 論理の飛躍を埋める

根拠を並べただけで結論に飛ばない。「AだからB」と書くときは、AがBを支える理由(Toulmin モデルの warrant)まで書く。

断定を避ける言い回しで飛躍をごまかさない。「〜と考えられる」で終わる文は、誰がどう確かめたのかを書くか、仮説だと明示するかのどちらかに直す。

## 6. 避ける表現

- 中身の薄い定型句 — 「〜が重要です」「包括的な」「一助となれば幸いです」「〜と言えるでしょう」「シームレスな」
- 定型の前置き — 「結論から言うと」「要点は3つ」「第一に、第二に、第三に」。たまに使うのは構わないが、節ごとに同じ型が並ぶと機械的に見える
- 中身に対して大きすぎる言葉 — 「革命的」「羅針盤」「まさに転換点」
- 締めだけ壮大 — 本文は具体的なのに、最後の一文だけ抽象的な決め台詞になる
- 括弧書きのタグ散らし — `(2026-10-13確認)` `(事実)` を本文に散りばめない。出典・調査日は節の先頭に1回だけまとめ、本文は普通の文章で書く
- 太字の多用 — 1つの節に何箇所もあると、どれも強調に見えず結局どこも強調されない
- 比較以外での表 — 箇条書きで足りるもの、1文で書けるものまで表にしない
- 絵文字、過剰な区切り線、コロンの多用
- 置き換えの効くカタカナ語 — 和語・漢語で言えるものはそちらを使う

## 7. リズム

文の長さを揃えない。短い文と長い文が混ざることで、どこが要点なのかが読み手に伝わる。

語尾を連続させない(「〜です。〜です。〜です。」)。言い回しを不自然に切り詰めない(「似ます」ではなく「似ています」、「向きます」ではなく「向いています」)。

## 委任先に文章を書かせるとき

サブエージェントに文章の成果物を書かせる場合、この skill を `~/.claude/agents/*.md` の `skills:` フィールドに入れてプリロードする(発火判断が不要になる)。`mermaid-rules` と同じ扱い。
