# 出力前の自己レビュー

作業した結果をそのまま出さない。草稿を作り、検証し、直してから出力する。

## なぜこの手順なのか

読み返して違和感を探す形のレビューは採用しない。外部の検証シグナルを持たない自己修正は品質を下げる方向に働き、正解を不正解へ書き換える方が逆より起きやすいことが報告されている(Huang et al., ICLR 2024。GPT-4 が GSM8K で 95.5 → 89.0 に低下)。眺めて直すだけなら、やらない方がましな場面がある。

効くのは、草稿を検証可能な問いに分解し、草稿を見ずに独立して答え、その答えで直す手順(Chain-of-Verification, Dhuliawala et al. 2023)。元の問いより個々の検証質問の方が正しく答えられるので、分解した時点で精度が上がる。草稿を参照させないのは、同じ間違いを写すのを防ぐため。

判定は点数ではなく二値で行う。「この回答の質は10段階でいくつか」は自己評価のバイアスを受けるが、「引用した行番号を実際に確認したか」は確認すれば答えが出る。

## いつやるか

やる — 調査報告、設計案、ドキュメント、PR説明文、コミットメッセージ、コード変更、複数段落の説明

やらない — 1行の回答、コマンド実行結果の報告、ユーザーへの確認質問

短い成果物でレビューを回すと、直す必要のないものを直してしまうリスクだけを負うことになる。

## 手順

1. 草稿を作る。まだ出力しない
2. 検証質問を立てる。草稿から「確かめられる主張」を抜き出し、問いの形にする
   - 引用したパス・行番号・関数名・設定値は実在するか
   - 「〜である」と書いた事実の出典はどこか。自分で確認したのか、そう書いてあるのを読んだだけか
   - コードなら、この変更で壊れる呼び出し元はないか。テストは通るか
3. 一次情報で答える。草稿を見ずに Read / Grep / テスト実行 / psql で独立に確認する。記憶で答えない
4. 食い違った箇所だけ直す。合っていた箇所は触らない
5. 下のチェックリストを通す
6. 修正が残っていればもう1周。2周で収束しなければ、残った不確かさを明示したうえで出力する

手順4は守ること。最も多い失敗は、正しく書けていた箇所を「もっと良く書けるはず」と触って壊すことで、修正の対象は検証質問と食い違った箇所に限られる。

手順6の上限は、際限ない書き直しを止めるために置いている。2周して決着しないなら自分で解決できる問題ではないので、分からないことを分からないと書いて出す。

## チェックリスト

7項目。増やすと項目どうしが干渉して判定が鈍るので、この粒度で固定する。

事実

- 未検証の推測を、検証済みの事実と同じ書き方で書いていないか
- 引用したパス・行番号・コマンド・設定値を、この会話の中で実際に確認したか

スコープ

- 頼まれていないことをしていないか。したなら、したと明示したか
- 頼まれたことで、やり残したまま黙っているものはないか

文章

- 段落を1つ消しても通ってしまう箇所はないか
- 根拠から結論への飛躍はないか
- `writing-rules` の「避ける表現」に当たるものはないか

## やらないこと

自分の出力を良し悪しで採点しない。自分が書いたものは自分にとって自然に読めるため、採点は当てにならない。見るのはチェックリストの項目だけ。

レビューの過程を出力に書かない。「自己レビューの結果、以下を修正しました」は読み手には要らない情報で、結果だけを出す。

修正のたびに謝罪や経緯を足さない。直したなら、直った状態を出す。
